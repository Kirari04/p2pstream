# Source discrepancy assessment, 2026-10-17

No source defect or production fix is established. The strongest concrete policy candidate is allowing a newly admitted logical stream to use a bounded larger share of an already reserved, grown aggregate session pool. Existing code can publish that share without allocating a larger pool, but no saved result shows that this removes the H2 penalty. It remains an optimization hypothesis, with fairness and demand-policy costs. Do not implement it or reopen rejected interventions from this assessment.

## Quantified growth difference and causal limitation

Both modes use two supporting demand epochs, at least one RTT per epoch, target eight times smoothed consumption times RTT, a >1.25-current eligibility threshold, at most doubling, and rounding to 64 KiB (`receive_window_growth.go:29-82`). A 512 KiB byte window with quarter-window recycling offers a nominal 384 KiB remaining flight budget when a normal update is first due, versus about 2.4 MB of 80 ms flight at 29.7 MB/s. This illustrates why initial growth matters; it is not a throughput upper bound in this asynchronous pipeline. Successive doubling to 16 MiB requires five decisions even when each proposal qualifies. Tiny handshake reads and consumption gaps enter the same demand estimator.

Legacy growth reserves additional per-stream receive storage and publishes one byte-window update (`legacy-source/internal/tunnel/growing_conn.go:55-80`). Aggregate growth on an insufficient pool reserves/allocates a session target of four times stream target, then sends session growth, allocation growth, and byte growth. On an already sufficient pool, it skips reservation, allocation and session growth, but still publishes allocation then byte (`internal/tunnel/growing_conn.go:167-212`). Each waits for local physical send completion, not a peer acknowledgement/round trip. Sequential methods cannot be assigned whole WAN RTT costs just by counting calls.

A roughly 4 MiB window at that RTT is already larger than that observed rate's BDP. Allocation charge amplification is independently refuted (1.00414 charge/payload); no reservation denial or publication error explains that history.

## Can an existing grown pool safely back earlier logical credit?

For target T <= min(stream maximum, current session receive limit / 4), the existing `AggregateReceiveWindowGrowth.Grow(stream,T)` path skips its reservation/slab/session-publication branch, validates ownership, then grows allocation before byte credit. Library checks enforce per-stream allocation <= quarter pool (`aggregate_window.go:811-850`) and the sender continues to consume bounded global credit. The storage backing is already reserved, so additional global payload storage is not required. This is a real source-backed distinction from legacy, where growing a new stream requires its own reservation.

It is not enough to assign a larger config default: doing that implicitly changes the negotiated initial promise on every stream, including sessions still at 2 MiB, and can violate the quarter-pool constraint. Any hypothetical early publication would have to happen after admission on the correct live stream using the existing checked method and owned lifetime. It must handle pool closure and ambiguous publication exactly as today. Direction-cold sequence 14 also needs consideration: only pre-seeding new connections changes the later receive direction if both directional endpoints were seeded; a server-only download optimization leaves upload symmetricity and fairness decisions unresolved.

Bounded global memory is necessary but not sufficient for equivalence. A larger allowance lets an unproven slow or hostile consumer occupy up to a quarter of the session pool, changes admission/fairness and the demand policy, and may increase burst/queue pressure or alter TCP history. Public input must never select an unchecked target. The policy could mask rather than fix a transport-history problem. No patch follows.

I found no published causal screen that specifically inherits an initial bounded logical allocation/byte target from an already grown pool while holding that pool's cap fixed. The reviewed growth/allocation artifacts are observational, not such an intervention. Several reviews broadly call growth-policy experiments closed; this review does not treat that wording as permission to repeat a closed experiment or as evidence that this exact candidate was tested. Root must resolve any unpublished predecessor before authorizing it. DATA split, refund split, queue-ack, deferred epoch and LOWAT screens changed different scheduling/physical boundaries and failed their primary retention gates. They neither establish nor exclude this policy candidate. The existing healthy standalone Yamux/raw-TLS results also prevent claiming that the fresh-stream ramp alone suffices to cause the public H2 regression.
