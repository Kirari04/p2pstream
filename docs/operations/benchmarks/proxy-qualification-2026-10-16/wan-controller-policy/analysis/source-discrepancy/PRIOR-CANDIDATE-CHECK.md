## Source ownership if a later design is justified

- The common policy owner is `internal/tunnel/growing_conn.go`. `NewAggregateGrowingConn:49-66` currently constructs state without publication or error return. `AggregateReceiveWindowGrowth.Grow:167-212` already serializes session ownership and retains irrevocable leases. For rounded target T <= current session receive limit/4, its reservation/slab/session-growth branch is skipped; allocation then byte publication still runs. Any design should keep that checked path and cap the target by operator/negotiated maximum. It must not change implicit initial protocol defaults in `newStream` or `NewAggregateYamuxConfig`.
- On the server, `public_routing.go:1020-1035` opens the stream after capacity acquisition, marks the lease live, obtains the exact lane/session growth owner and constructs the wrapper. `agent_request_limiter.go:40-65` joins GrowingConn and capacity release ownership. An explicit publication failure needs the existing terminal fencing/lifetime discipline (`:68-85`), rather than returning the slot while credit might remain live. The current constructor cannot silently hide a publication error.
- On the agent, `agent.go:1359-1375` constructs the wrapper only after stream capacity admission, then parses/handles the open request and finally releases capacity after peer close. Any proposed grant must retain correct admission/class/destination-validation boundaries and error cleanup; a generic constructor-side unconditional grant would also affect malformed, rejected or control-like streams unless explicitly constrained.
- Physical pool owners are created once per session at `server.go:1014` and `agent.go:1140`; keep their lease-until-session-close ownership. The protocol/library quarter-share checks are `aggregate_window.go:811-850`; bounded global send/receive credit remains `:211-247,334-355`. Pool availability is not proof of fairness: larger idle/new-stream allowances can let four unproven consumers compete for the entire pool.
- Both endpoints and receive directions matter. Pre-seeding only the server's new download connection does not define symmetric upload behavior; sequence 14 revisits an upload stream whose server receiver is direction-cold. A policy must state whether any grant happens once per admitted stream, once per receive direction, or on demand. HTTP request direction is not available as a trustworthy policy selector in generic Yamux.
