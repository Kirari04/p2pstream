# Resolver-owned context allocation screen (pre-execution)

Baseline is immutable tracked Go source at 8fa16378af4ac0117276726fe6e51d8bc4c74c85; all 430 existing source inputs are byte-verified against the prior route-reuse validation inventory. Baseline and candidate each add the identical focused test/benchmark overlay. Only candidate internal/server/client_identity.go differs. No worktree production source changes are made.

Profile support: the native-pair production profile attributes 210,285,452 cumulative allocated bytes (511 B/completion) to resolvePublicRequestIdentity inside initializePublicProxyContext. Existing ResolveRequest creates two context value nodes, boxes the identity and header slice, copies a fresh resolver result's MatchedSources, and copies the immutable configured header list twice before attaching the shallow request copy. These are distinct from the retained recorder nullable-ID reduction and rejected SQL grouping experiments.

Candidate stores only the freshly resolved identity and immutable resolver header names in one private context that embeds its parent. Private key Value lookups return that context pointer; exported getters recognize it and preserve defensive copies. Existing WithClientIdentity and withClientIdentityHeaderNames remain unchanged, including descendant overrides; old context values and nil/invalid lookups still work. All other values and Deadline/Done/Err delegate to the parent. Public helpers' results remain the observable contract. The context is allocated per request and is never pooled.

No SQL, persistence, event fields, limits, admission, policy parsing or schedules change. This candidate does not change header sanitization or trust resolution. Retaining resolver header names is safe under the existing immutable resolver contract; every exported header read still copies. Existing trust/consumer tests and new ownership, precedence, cancellation, concurrent access and retained-lifetime checks gate that assumption.

## Fixed screen

Compile separate baseline/candidate test executables offline with pinned Go 1.26.6 and existing dependency/build caches, taskset 8-11, GOMAXPROCS4, go test -mod=readonly -p=2 -c. Run the same selected identity and consumer tests normally on both; run candidate tests under race once. Build/test failures stop before timings and remain recorded.

Run 10 alternating-order pairs (AB/BA repeated five times), each executable pinned to CPU8/GOMAXPROCS1. Every invocation runs all 28 benchmark cases once, 150ms per case: seven request/configuration shapes, background/deadline parent, ResolveRequest alone and ResolveRequest plus exported reads. Shapes cover zero, one, two and four configured headers; direct, invalid peer, configured untrusted, trusted single-IP, trusted chain, conflicting sources and disabled sources. Inputs/resolver/deadline creation occur outside timed ranges. A benchmark operation is exactly one full ResolveRequest (and both exported readers in the read case); setup/migration/helper work is excluded.

Predeclared retention: every case must save at least 32 B and 2 allocations/op; all per-case candidate/baseline median ns/op ratios must be <=1.03; each paired case ratio must be <=1.10. These are an allocation/no-regression screen, not whole-application throughput proof. Preserve every invocation and sample; a failing cell rejects the candidate without selective retry or E2E advancement. Expect configured cases to save more memory by eliminating redundant header copies. No benchmark execution has occurred when this proposal is written.

Each compile has a 300-second outer limit; semantic/race commands have a 180-second inner timeout and 240-second outer limit; each benchmark invocation has a 120-second outer limit and 90-second test timeout. Commands execute serially only after the coordinating root grants a slot. Raw logs, exit statuses, hashes, manifest and parsed screen decisions stay under this directory. Root separately reviews and applies production changes after the source freeze, if retained.
